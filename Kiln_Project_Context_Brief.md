## 1. The project

**Title:** A Kiln on Schedule — Understanding Traditional Firing through Algorithms

**Goal:** To make the ingenuity and interconnected working of the Hoffmann kiln visible, understandable, and engaging by translating its systems of structure, heat, time, and sequencing into an interactive experience.

**What I am building now:** a standalone interactive web page (the digital component). A physical model (8-chamber kiln with LEDs and tiles) may follow later, but the digital piece must work fully on its own and must be both visually impressive and clear.

**The test of success:** after two minutes, a visitor can explain in their own words that:
1. the fire travels around the kiln while the tiles stay still,
2. every chamber is at a different stage at the same moment,
3. heat is reused (it does useful work twice),
4. one empty or unready chamber affects the rest of the ring.

## 6. Core functionality

1. **Run the firing cycle.** 8 chambers; the fire advances one chamber per tick (1 tick = 2 simulated hours). Each chamber's stage comes from its position relative to the fire: firing, preheating (ahead), cooling (behind), wait/unload/reload. Window sizes are settings.
2. **Simulate heat per chamber.** A simple temperature per chamber, updated many times per tick. The firing chamber gains heat from fuel; hot gas carries heat forward to the chambers ahead; air drawn in behind cools fired chambers. Peak sits within the 850–900 °C band. A relative **fuel index** counts fuel used.
3. **Control time.** Play, pause, step one tick, speed control, drag around the ring to scrub forwards and backwards in whole ticks. Every tick is saved, so scrubbing back replays history.
4. **Space–time chart.** Built from saved history. Firing front = diagonal; stall = kink.
5. **Heat moving and being reused.** Particles follow the air path (in behind the fire → through cooling chambers → past the fire → through preheating chambers → out the chimney). Colour follows temperature. A **recovery switch** sends exhaust straight to the chimney: chambers ahead stay colder and the fuel index rises.
6. **Dependency.** Chambers can be emptied and reloaded. When the fire reaches an empty chamber, the simulation pauses and offers: **wait** (clock holds, neighbours drift), **skip** (fire jumps ahead), **fire empty** (fuel is spent on nothing). The card states plainly that what Kundapur does is unknown. Consequences are modelled and labelled as such.
7. **Explain and qualify.** Context panel with one or two lines about what is happening and why. Evidence mode (section 8).

## 7. Interaction principles

**This is not a game.** No score, no target, no "correct" way to run the kiln, no win state, no optimisation goal. Every interaction must answer: *"What does this help the user understand?"* If it can't, cut it.

| Interaction | What it helps the user understand | Kept out on purpose |
|---|---|---|
| Play, pause, step | The fire moves while tiles stay still; each tick changes every chamber at once | — |
| Speed control | The rhythm of the cycle | Any sense that faster is better |
| Drag ring to scrub | Time is cyclic; moments can be compared | — |
| Click a chamber | What it is doing now and which chambers it depends on | Per-chamber "performance" |
| Layer tabs | Structure, time, heat and dependency are separate systems in one kiln | — |
| Recovery switch | Heat does work twice; without reuse, chambers ahead start cold and need more fuel | Fuel index shown as a side-by-side comparison, not a score to minimise |
| Empty a chamber | Chambers are coupled: one gap affects the whole ring | — |
| Wait / skip / fire-empty | Each choice moves the problem somewhere else; Kundapur's practice is unknown | No choice marked right or best; consequences shown, never graded |
| Show evidence | What is observed, borrowed, assumed, simulated or unknown | Labels in normal mode |

## 8. Evidence mode

- **Normal mode** shows no evidence labels. It prioritises clarity and engagement.
- A **"Show evidence"** toggle switches to evidence mode, which restyles each element by its source and shows a small legend:

  - **Literature** (L) — e.g. dashed
  - **Assumption** (A) — e.g. paler
  - **Simulation** (S) — e.g. bands/spreads
  - **Unknown** (U) — e.g. fogged or hatched

The emptiness that remains is itself a finding.~~ — **built and then cut on day 11.** It worked, and it reached the drawing as well as the labels. What it could not do was share a band with the legend: a key and a switch side by side made the legend read as a control panel rather than as a key, and the mode is about understanding the picture, not operating it. What the filter was there to show — how little of this was observed — is now stated outright, with counts, in the details sheet below. Saying it is clearer than making someone find it.
- **Revised day 12: the letter is the only restyling.** Fading each element by its source (assumption paler, unknown hatched) was built and dropped. It read as low contrast rather than as provenance: the assumed labels on the kiln looked broken, not chosen. In evidence mode every tagged thing now keeps its ink and gains one chip, the same mark on the kiln labels, in the side panel, in the legend and in the details sheet. The legend shows the five codes only. How many parts carry each one is in its tooltip and, in full, in the details sheet.
- Tags are stored in `config.js` in both modes; the two modes draw the same model.
- **Added day 11:** a **details sheet** behind the legend. A tag says a figure was simulated; it does not say what was done to it, and "simulated" stretches from a defensible rule to a number picked because something had to be drawn. The sheet lists every tagged value with its source, and `config.js` `METHODS` describes how each computed figure is arrived at. It is generated from the config, so it cannot drift from the model.

## 9. Visual direction

- **One hero, not a dashboard.** The ring dominates; everything else is quieter.
- **Motion only where something is happening.** Every moving pixel is fire, air or a tile. No decorative drift.
  - **Day 11:** and the clock hand, which is a fourth thing. It is not drift — it is the simulation's own clock, and it stops dead whenever simulated time does — but the rule should say so rather than have the next reader find a hand moving and conclude it lapsed.
- **Palette with meaning:** charcoal and clay as the ground; a blackbody heat ramp (dull red → orange → yellow-white) used **only** for temperature; one cool pale tone used **only** for air.
  - **One exception, day 11:** the clock dial flashes `--heat-4` when the fire moves. The flash lands at the instant the fire arrives in the next chamber, so it marks a heat event, and borrowing the burning chamber's own red ties the dial to the kiln. Any other red would be decoration and would need arguing for separately. The dial is otherwise outline-only in sand, and nothing else on the page may spend the ramp.
- **Glow driven by the simulation:** chamber brightness/bloom comes from simulated temperature, so the beauty is the data.
- Clean, confident typography; flat surfaces; no gradients or shadows for decoration.
  - **Day 12:** one typeface, Archivo, bundled locally in `kiln/vendor/fonts/` so the exhibition laptop needs no internet. Its width axis does the work of a second font: a wide, heavy wordmark, like a sign painted on the building, and narrow caps for the markings on the kiln (part labels, evidence chips, chart axes). Everything a visitor reads is in sentence case. Charcoal is the kiln's ground and clay is the reading column's. The palette rules above are unchanged.
- Polish happens on days 11–12. Before that: plain shapes and flat colours.
- References: Low-Tech Magazine "Rings of Fire: Hoffmann Kilns" (step-by-step drawings of the fire and dampers advancing): https://solar.lowtechmagazine.com/2009/10/rings-of-fire-hoffmann-kilns/

## 10. Architecture

**Rule: all kiln logic lives in `engine.js`. Views only read state and draw it.** Inputs send named actions; the engine applies them.

```
inputs (mouse/touch, buttons; later Arduino via Web Serial)
   → actions (tick, setPaused, setSpeed, scrubTo, emptyChamber, loadChamber,
              setRecovery, setAutoLoad, chooseForkPolicy,
              setEvidenceMode, setDetails)
   → engine.js (state + step(dt) + dispatch(action))  ← config.js
   → history.js (one snapshot per tick)
   → views: ring + particles (p5), space–time chart (D3), panel + fork card (HTML)
```

**Folder structure**

```
kiln/
  index.html        layout and controls
  style.css         palette, type, evidence styles
  config.js         all values + evidence tags + open-question settings
                    + how each simulated figure is computed (METHODS)
  engine.js         state + step(dt) + dispatch(action) — no drawing code
  history.js        snapshots for scrubbing and the chart
  views/ring.js     p5: ring, glow, drag-to-scrub
  views/heat.js     p5: particles on the same canvas
  views/chart.js    D3: space–time chart
  views/panel.js    context text, fork card, switches
  views/evidence.js the legend, and the details sheet behind it
  views/clock.js    the dial in the transport bar
  main.js           loop: input → engine.step → render views
```

**Engine state (starting point)**

```js
state = {
  tick: 0, subTime: 0,            // whole ticks + progress within one
  firePos: 0,                     // chamber index 0–7
  chambers: [ { loaded: true, temp: 30, stage: 'preheat' }, ... ],  // 8
  params: { tickSeconds: 3, recovery: true, policy: null, window: { pre: 3, cool: 2 } },
  fuelIndex: 0,                   // relative units
  paused: false, fork: null,      // fork set when the fire meets an empty chamber
  ui: { evidenceMode: false, details: false }
}
```

**Console checks to keep passing:** after 8 ticks the fire is back where it started; each chamber fires exactly once per loop; an empty chamber always triggers the fork.

The Arduino (later) will be one more input sending the same actions; the physical LEDs will be one more view. Nothing else should need to change.
